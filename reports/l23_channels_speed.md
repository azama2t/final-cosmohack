# Модели на подмножествах каналов и лёгкая быстрая модель

Рецепт один и тот же для всех строк: рецепт итоговой модели (`weights/lgbm/meta.json`: MARIDA train + MADOS train+val без сцен, совпадающих по месту с val MARIDA; классы, которые есть только в MADOS, не размечены; квоты на классы; pos_weight 3; LightGBM 400 деревьев × 63 листа). Оценка: val MARIDA, все размеченные пиксели вместе, порог подбирается по val (сетка 0.02..0.98). Test MARIDA не читался. Проверка воспроизводимости: (e) seed 0 дал **F1 0.9226, IoU 0.8564, порог 0.63** — это совпадает с итоговой моделью бит в бит.

Признак берётся в подмножество, только если все его входные каналы есть. FDI требует B6/B11, FAI и NDMI требуют B11, BSI требует B11. Для RGB в проекте вычислим только индекс SI, поэтому для RGB добавлены 26 своих признаков, которые считаются только из RGB: BRI = (B2+B3+B4)/3, NDGR = (B3−B4)/(B3+B4), NDBG = (B2−B3)/(B2+B3), для каждого среднее и std в окнах 3/7/15, плюс разность с локальной медианой (BRI 15/31, NDGR 15/31, NDBG 31). Оконный код тот же, что в `features/pixel.py`. Кэш: `out/l23_cache/*_rgbx.npz`; порядок пикселей сверен с кэшами LightGBM-MARIDA и эксп. 13.

### Скорость, 300 чипов 256×256 (первые 300 патчей val MARIDA, `out/speed_chips`), только CPU, 10 потоков

CPU на i5-13600KF общий с другими задачами, поэтому сравнивать можно только строки внутри одного прогона.

Замеры в `scripts/experiments/l23_speed.py`: новый процесс; чтение → только нужные признаки (бит в бит как `pixel.py`) → `lightgbm.Booster.predict` → запись prob и mask в tif. «Холодный» — худший из 2 запусков; «тёплый» — второй проход в том же процессе.

| модель | признаков | деревьев | холодный, с | стадия модели, с | тёплый, чипов/с |
|---|---|---|---|---|---|
| итоговая `weights/lgbm` | 48 | 400 | 50.6 (44.9) | 37–39 | 6.9 |
| **лёгкая k20_t200_l31** | 20 | 200 | **16.8** (13.9) | 9–11 | **19.0** |
| k20_t100_l15 | 20 | 100 | 14.6 (8.8) | 4–5.6 | 20.9 |
| k48_t100_l15 | 48 | 100 | 23.8 (19.4) | 8.4–9.1 | 19.7 |

Опора — продуктовый `inference.py --device cpu --workers 10` с итоговой моделью (ctypes lib_lightgbm): холодный запуск **25.7 / 27.0 с**. Мой замер медленнее продукта: пакет lightgbm для Python предсказывает примерно в 1.5 раза медленнее, чем ctypes.

Путь через продуктовый предиктор (`l23_product_speed.py`: `LGBMPredictor`, ctypes, 10 потоков, тёплый прогон, все 48 признаков):

| модель | признаки (1 поток), с | модель (10 потоков), с | модель, чипов/с |
|---|---|---|---|
| итоговая | 8.9 | 24.4 | 12.3 |
| лёгкая k20_t200_l31 | 8.4 | **9.0** | 33.5 |
| k20_t100_l15 | 8.4 | 3.7 | 81.6 |

Оценка для продукта: лёгкая модель в `inference.py` сокращает стадию модели примерно на 15 с. Холодный запуск был бы примерно 11–12 с вместо 26 с на этом CPU (10 потоков). Это оценка, прямого замера нет: в `inference.py` нет флага выбора весов.

Все команды запускать из `scripts/experiments` с `PYTHONPATH=../../src` через `../../.venv/Scripts/python.exe`. Каждая занимает 5–15 с, если есть кэши `out/l3_cache`, `out/l13_cache` и `out/l23_cache` (последний строится командой `python l23_common.py` примерно за 80 с). Чтобы подготовить веса для другого набора каналов, нужно переобучение, которое эксп. 23 уже провёл.

Ограничения. Порог подбирался по той же val, что и оценка: так же делается и для итоговой модели, но для урезанных наборов оценка слегка оптимистична. Все данные — ACOLITE rhorc; RGB у организаторов может быть в L2A или 8-битным «визуальным» продуктом, и тогда потеря будет больше. Leave-region-out для урезанных наборов не проверялся.
