## 2. Скорость (300 чипов val, холодный старт, `inference.py --weights DIR`)

Серия `scripts/experiments/l31_speed.py` → `weights_exp/l31/speed.json`:
- 3 повтора;
- в каждой конфигурации модели идут парой подряд, порядок в паре чередуется между повторами;
- в таблице медиана из 3 прогонов.

Как задаются потоки: «CPU N потоков» — это маска affinity процесса на первые N логических CPU, как `start /affinity` в `docs/CRITERIA.md`. `inference.py` видит N CPU. lib_lightgbm работает в N потоков, пул — в min(N, 8) (`--workers` по умолчанию). Так моделируется машина с N потоками. Флаг `--workers N` сам по себе число потоков LightGBM не ограничивает.

Железо: i5-13600KF, RTX 4070, Windows 10. Параллельно работали другие дорожки: первый повтор на 8 потоках у обеих моделей на 4–5 с медленнее.

| | CPU 4 потока | CPU 8 | CPU 20 | GPU |
|---|---|---|---|---|
| итоговая | 81.1 с (74.8 / 81.6 / 81.1) | 37.9 с (42.5 / 37.9 / 37.1) | 21.7 с (21.0 / 22.0 / 21.7) | 5.65 с |
| k20_t400_l63 | 77.3 с (74.0 / 77.3 / 78.0) | 35.9 с (40.5 / 35.9 / 35.0) | 20.4 с (19.6 / 20.4 / 20.8) | 4.28 с |
| ускорение | ×1.05 | **×1.06** | ×1.07 | ×1.32 |

Эквивалентность внутри модели: все прогоны повтора 0 (CPU 4/8/20 и CUDA) против первого прогона той же модели дают max|Δprob_u8| = 0 и 0 px в маске.

Почему ускорения нет. Из `--profile-json`, поток·с:

| | predict, CPU 8 | признаки, CPU 8 | predict, GPU | признаки, GPU |
|---|---|---|---|---|
| итоговая | 35–40 | 33–41 | 2.3–2.5 | 26–28 |
| k20_t400_l63 | 33–39 | 25–30 | 1.1–1.2 | 17–18 |

- На CPU стена процесса почти равна времени predict: lib_lightgbm, 19.7 млн пикселей × 400 деревьев × 63 листа.
- Признаки (−25 % поток·с) считаются в пуле параллельно с predict и в стену почти не входят.
- Цена predict определяется числом деревьев и их глубиной, а не числом признаков. Поэтому у k20_t400_l63 CPU-predict почти тот же.
- На GPU predict маленький, поэтому экономия на признаках видна: ×1.32.

## 3. Правило замены

| условие | порог | k20_t400_l63 | итог |
|---|---|---|---|
| F1 val ≥ 0.9226 − 0.005 | 0.9176 | 0.9216 (s0), 0.9223 (3 seed) | да |
| LRO ≥ 0.8435 | 0.8435 | 0.8492 | да |
| CPU 8 потоков, холодный старт, ускорение ≥ ×1.3 | ≤ 29.2 с | 35.9 против 37.9 с = ×1.06 | **нет** |

**Решение: не заменять.** `weights/lgbm`, `reports/speed.md/json` и эталон в `tests/test_speed_equivalence.py` не менялись, бэкап не создавался.

Что это значит для CPU-критерия. Чтобы на 8 потоках было ≤ 29 с, стадию predict на CPU нужно сократить примерно на 30 %: около 280 деревьев × 63 листа или 400 × ~40 листьев. Это отдельный эксперимент с LRO. По L23/L26 урезание деревьев и листьев бьёт по LRO сильнее, чем урезание признаков: k20_t200_l31 0.824, k48_t100_l15 0.829. Промежуточные варианты (k48 или k20, 250–300 × 47–63) не проверялись.

## 4. `--weights DIR` в `inference.py`

- Флаг `--weights DIR` задаёт папку весов (`model.txt` + `meta.json`), по умолчанию используется `weights/<model>`, как раньше. Значение уходит в загрузчик реестра (`get_predictor(..., weights=DIR)`), без флага kwargs прежние.
- Модель на подмножестве признаков загружается автоматически: `LGBMPredictor` берёт `meta.features`. Выход модели не меняется, а серия замеров выше шла именно через этот флаг.

## 5. Порог смещения L2A в `--scale auto`: 1000 → 500 DN

Изменение в `inference._boa_offset_rule`:
- новая константа `BOA_DETECT_DN = 500`;
- вычитается по-прежнему `BOA_OFFSET_DN = 1000`;
- если медиана B12 по тёмным пикселям ≥ 500, вычитаем 1000 DN; при медиане 500–1000 в лог дописывается «water slightly below 0 after subtraction, usual for L2A»;
- строка «ambiguous 500..1000» убрана.

Входы в reflectance правило не затрагивает: оно вызывается только для DN-файлов (медиана > 2).

**Обоснование** (`scripts/experiments/l31_boa_evidence.py` → `weights_exp/l31/boa_evidence.json`). Статистика правила посчитана самим `_boa_offset_rule` на `DN = rint(ρ·1e4)` без смещения и с `+1000`:

| источник | без смещения: min / p50 / p99 / max | со смещением: min / p50 / max | правило 1000: ложных / пропусков | правило 500: ложных / пропусков |
|---|---|---|---|---|
| 48 живых сцен L2A (`data/live`, отрицательные ρ сохранены) | 8 / 22 / 827 / 1352 | **1005** / 1020 / 1234 | 1 / 0 | 1 / 0 |
| 300 чипов MARIDA val (ACOLITE) | 12 / 46 / 210 / 851 | **1012** / 1046 / 1851 | 0 / 0 | 2 / 0 |

- **Главный аргумент за 500.** Со смещением минимум по живым сценам 1005 DN, то есть запас правила 1000 всего 5 DN (0.0005 reflectance). У L2A вода бывает чуть отрицательной: в живых сценах есть ρ до −0.1. Сцене с водой при ρ_B12 ≈ −0.001 хватит, чтобы правило 1000 пропустило смещение. Тогда вся сцена сдвинута на +0.1, а в L24 такой сдвиг давал находки 232 → 0. У правила 500 запас с этой стороны ≥ 505 DN.
- Тест `test_l31_boa_offset_threshold_500`: на воде с ρ_B12 ∈ [−0.009, 0] и смещением медиана 958 DN. Старое правило даёт offset 0, новое — −1000, выход после вычитания верный.
- **Цена.** Чипы без смещения, где «тёмные» пиксели — суша или облака, попадают в зону 500–1000: MARIDA val `S2_11-6-18_16PCC_34` (B8 med 0.32) даёт 851, `S2_18-1-18_48PZC_0` (B8 med 0.098) — 501. На DN-входе без смещения это 2 из 300 чипов (0.7 %), и все они не водные. Живая сцена `haiti/2026-01-09` (B8 med −0.002, сцена битая) даёт ложное срабатывание при обоих порогах.
- В воде без смещения медиана 10–240 DN (p99 = 210 на val). Порог 500 в два раза выше этого уровня.
- Возможное усиление, не делалось: при медиане 500–1000 дополнительно проверять долю пикселей B8 < 1000 DN. Без смещения это вода и таких пикселей много, со смещением их почти нет.
