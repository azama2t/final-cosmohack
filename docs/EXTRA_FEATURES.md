# Дополнительные функции (критерий О6)

Каждая функция описана по схеме: потребность → как работает → связь с основным сценарием (снимок + полевое наблюдение →
маска качества → детекция → зона/оценка) → доказательство. В конце каждого раздела указано, что не валидировано.

## 1. Поиск синхронной сцены для полевого наблюдения (L71, новая)

- **Потребность.** У специалиста есть новое или планируемое наблюдение (точка или трансекта, время). Нужно понять, есть ли снимок
  S2/Landsat, достаточно синхронный с учётом дрейфа, и не закрыта ли полоса облаками или бликом.
- **Как работает.** `POST /api/v3/pairfinder`, CLI `scripts/case/pairfinder.py`, логика `src/macroplastic/case/pairfinder.py`.
  Поиск по STAC идёт через общий кэш `data/pairs/cache`, офлайн-режим — `MACROPLASTIC_PAIRFINDER_OFFLINE=1`. Для каждой
  сцены функция считает dt, смещение воды по сценариям дрейфа, допуск и решение о синхронности с причиной. Отдельно
  выдаётся окно синхронизации |dt| ≤ допуск / (3.6 × скорость): 4.17 ч для 0.2 м/с и 3 км. Если время не задано,
  функция выдаёт интервал UTC, в который наблюдение должно попасть. Если дата в будущем, пролёты предсказываются по периоду
  повторения орбиты. С `quality=true` для 1–3 лучших сцен считается маска качества в полосе наблюдения кодом L61.
- **Связь с основным сценарием.** Функция применяет правило допуска по дрейфу (раздел 2) к новому наблюдению, до того как
  строить пару и проверять детекции.
- **Доказательство.** `reports/case_pairfinder/evidence.md`. Наивное окно ±1 сут даёт 29 «пар», из них синхронных 0.
  Окно синхронизации на тех же 318 событиях выдаёт 12 событий Чёрного моря с конкретными интервалами UTC; у 8 из них полоса
  чистая по маскам. Ещё 2 события Северного моря синхронны (|dt| 0.8–2 ч), но их полоса на 100 % под облаком. Реестр
  отбрасывал их по облачности всей сцены, функция показывает причину в полосе.
  Прогноз пролётов на архиве совпал с реальной съёмкой в 82 из 88 случаев (±5 мин).
- **Не валидировано.** Скорость дрейфа сценарная, а не измеренная. Для S4 результат условный, потому что время трансект
  неизвестно. Прогноз не учитывает манёвры орбит и облачность.

## 2. Допуск синхронности пары по дрейфу (L59b)

Для каждой пары «наблюдение ↔ сцена» считается смещение плавающего материала: (течение + доля ветра) × |dt|, сценарии
low/typical/high со ссылками на литературу. Пара принимается, только если смещение не больше допуска (ширина полосы / 2
+ 3 км). Смысл: пара по метаданным «±1 сут» ещё не проверяет детекцию в точке, потому что вода за сутки уходит на ~17 км
при 0.2 м/с. Доказательство — `reports/case_pairs/summary.md` (раздел «Допуск по дрейфу»): из 29 принятых по метаданным
событий при типичном сценарии остаётся 0. В мягком варианте (допуск = ½ длины трансекты) остаётся 2.
Не валидировано: скорости взяты из литературы, а не из ERA5/CMEMS в точке.

## 3. Сохранённые запросы и ссылка на вид

Фильтры карты (даты, источники, профиль, статус) сохраняются как запрос (`POST/GET/DELETE /api/v3/queries`,
`GET /api/v3/queries/{id}/run`). Сохранённый запрос перезапускается одной кнопкой, по нему же делается экспорт
(`/api/v3/export?query_id=`). Состояние карты (район, дата, слои, камера, выбранный объект) кодируется в URL
(`service/frontend_v2/src/lib/url.ts`), поэтому ссылкой можно поделиться, и коллега увидит тот же вид. Потребность — повторяемая
проверка одного и того же района или выборки без ручного набора фильтров. Постановка требует это напрямую
(«сохранить и перезапустить запрос»). Доказательство — тесты `tests/test_api_v3.py` (сохранение, запуск, экспорт по query_id).
Не валидировано: удобство на реальных пользователях не проверялось.

## 4. Фильтр артефактов и ручной отсев следов судов

Правила L37/L43 (`src/macroplastic/grid/artifacts.py`) помечают швы снимка, кильватер и суда полем `artifact`
(seam/wake/ship). Помеченные объекты не удаляются, но исключаются из зон, H3-индекса и числа уверенных находок. То, что
автоматика пропустила, отсеивается вручную по вырезкам (`configs/manual_artifacts.yaml`). Потребность: линейные
артефакты выглядят как «строки мусора» и поднимают ложные зоны на первое место. Доказательство — `reports/artifacts.md`
(индекс районов было → стало, например Гуанабара 0.42 → 0.24 ‰; подтверждённых второй моделью объектов MDD 360 → 297
по правилам L37, затем 297 → 294 после правила кильватера) и `reports/manual_review.md`
(6 ручных пометок: Гондурас 3, Мумбаи 1, Лагос 2, у каждой вырезка и причина).
Не валидировано: правила подобраны по нашим сценам. Разметки артефактов для метрики полноты и точности нет.

## 5. Проверка человеком (очередь сомнительных находок)

`service/review.py`: очередь сомнительных детекций, метки (мусор / пена / водоросли / судно / облако / другое) с
происхождением (кто, когда, сцена, модель, вероятность), кнопка «ложное» на карте и фоновое дообучение
(`scripts/retrain_with_labels.py`). Потребность: специалист исправляет модель на своём районе, а не только смотрит на неё.
Связь: метки попадают в тот же слой находок и в обучающую выборку. Доказательство — `reports/tasklog/19_backend.md`
и тесты `tests/test_api_review.py`.
Не валидировано: эффект дообучения на реальных метках пользователей не измерялся, меток пока мало.

## 6. Режим «Живые снимки»

Свежие сцены Sentinel-2 L2A (STAC Earth Search, запасной источник — Planetary Computer) по выбранным районам: вырезка
~25×25 км, маска воды по SCL и NDWI, спектральная маска облаков, две модели (MDD и LightGBM), дрейф найденных объектов.
Потребность: оператору нужно смотреть на текущую обстановку, а не только на архив MARIDA. Доказательство —
`reports/report.md` (64 снимка, 18 районов, из них 52 за 2025–2026 гг.) и `reports/tasklog/06_live.md` (совпадение MDD с
эталонным предсказанием авторов, r = 0.886 для Дурбана).
Не валидировано: разметки на живых снимках нет. Это слой для сервиса, а не оценка качества детектора.
