# spec.md — что строим и зачем

## 1. Продукт одной фразой

Система мониторинга природных пожаров по спутниковым данным: находит пиксели активного горения на снимках VIIRS, строит контуры гарей с тремя степенями поражения по Sentinel-2/1 и показывает всё это на веб-карте со справкой по площадям и выгрузкой векторов.

## 2. Пользователи

| Пользователь | Что ему нужно |
|---|---|
| Организаторы / жюри (проверка) | Одной командой получить `submission.csv` на скрытом тесте, быстро (< 30 с) и воспроизводимо; прочитать отчёт и README; запустить сервис |
| Аналитик мониторинга (лесная охрана, МЧС) | Выбрать территорию и интервал дат → увидеть термоточки и гари на карте, площадь по степеням, выгрузить контуры |
| ГИС-специалист | REST API: GeoJSON / Shapefile с атрибутами id, класс, площадь; справка JSON/CSV |

## 3. Сценарии

- **С1. Проверка решения.** Распаковать тест → `python inference.py --data-dir data/test --output submission.csv` → код 0, файл валиден, время < 30 с на GPU, повторный запуск и CPU дают тот же файл.
- **С2. Аналитик на карте.** Открыть `http://localhost:8000` → нарисовать полигон или прямоугольник (или вставить bbox), выбрать даты → термоточки (раскраска по температуре I4), гари (раскраска по степени), контур события; слева справка: площадь гари в га всего и по степеням, число термоточек; кнопки выгрузки GeoJSON / Shapefile / CSV. Кнопка «Демо-запрос» выполняет готовый пример.
- **С3. ГИС через API.** `GET /api/v1/burn-scars?bbox=…&date_from=…&date_to=…&format=geojson|shp`, `GET /api/v1/hotspots…`, `GET /api/v1/summary…&format=json|csv`, `POST /api/v1/query` (bbox или GeoJSON-полигон) → слои в EPSG:4326, площади посчитаны в UTM.
- **С4. Воспроизведение обучения.** `python train.py --module af|bs|all` на `data/train` → веса в `weights/`, метрики в журнале.
- **С5. Защита.** Докладчик за 4 минуты по деку 8–12 слайдов показывает задачу, решение, цифры, демо.

## 4. Функции и критерии приёмки

Метрика (plan.md §3.1): `Score = 0.35·F1_af + 0.35·IoU_burn + 0.30·mIoU_sev`. «AF-часть» = 0.35·F1_af, «BS-часть» = 0.35·IoU_burn + 0.30·mIoU_sev.

### F1. Чтение данных (`src/firemon/io.py`)
- Читает AF- и BS-чипы в словарь массивов (C, H, W) + имена каналов из band descriptions.
- Понимает обе раскладки `meta.csv` (train: `af/meta.csv` и `bs/meta.csv`; test: один `meta.csv` в корне с `kind`).
- Работает с каталогами `aux` на Windows (`win_path`).
- **Приёмка:** тест читает по одному чипу каждого типа из train и test, проверяет формы (8,256,256)/(5,256,256) для AF и (10,512,512)/(2,512,512)/(3,512,512) для BS; чтение 1 BS-чипа < 0.3 с.

### F2. RLE и сабмит (`rle.py`, `submission.py`)
- RLE: нумерация с 1, построчно (row-major), пары `start length` по возрастанию, серии не пересекаются и не соприкасаются, без выхода за H·W; пустая маска — пустое поле.
- Сабмит: заголовок `chip_id,class_id,rle`; ровно строки шаблона `sample_submission.csv` в его порядке (AF: class_id=1; BS: 1,2,3); текстовый формат — **как в `example_submission.csv`** (колонка `rle` без кавычек, пустая маска — пустое поле, переводы строк CRLF). Маски классов BS не пересекаются.
- Валидатор: число строк 447, все chip_id из шаблона, RLE корректен.
- **Приёмка:** декодирование `example_submission.csv` и обратная сборка дают побайтно тот же файл; тесты на каждое правило RLE (пустая маска, вся маска, соседние серии, последний пиксель).

### F3. Метрика (`metrics.py`)
- F1_af, IoU_burn, mIoU_sev, Score — микро-усреднение по пулу пикселей всех чипов; пустой знаменатель → 1; класс есть в эталоне, нет в предсказании → IoU = 0.
- CLI: оценка файла сабмита по каталогу масок.
- **Приёмка:** юнит-тесты на крайние случаи; сабмит из истинных масок даёт Score = 1.0.

### F4. Валидация (`splits.py`, `configs/folds_*.csv`)
- AF: GroupKFold-5 по тайлу (группы — одинаковый охват `x_min,y_min,x_max,y_max,epsg`). BS: GroupKFold-5 по пространственным блокам 50×50 км. Временной сплит: val = чипы 2024 года, train = остальные.
- Файлы фолдов создаются один раз (seed 42) и коммитятся.
- **Приёмка:** нет пересечения групп между фолдами; фолды сбалансированы по числу чипов ±20 %.

### F5. Модуль AF — активные очаги
- Вход: AF-чип. Выход: маска 0/1 (256×256).
- Решение — plan.md §4: кандидаты по порогам день/ночь → признаки → LightGBM (5 фолд-моделей) → порог по OOF. Запасной вариант — контекстное правило.
- **Приёмка:** OOF F1_af ≥ 0.95 (групповой) и ≥ 0.94 (временной); инференс 180 чипов ≤ 6 с; без весов — откат на правило с ошибкой в логе.
- Цель по качеству (достигалось): F1 0.968 / 0.960.

### F6. Модуль BS — гари и степень
- Вход: BS-чип. Выход: маска 0–3 (512×512).
- Решение — plan.md §5: UNet (resnet34) выбирает «свой» пожар, стек LightGBM 2-го уровня восстанавливает границы и степень, пороги, постобработка.
- **Приёмка (минимум):** OOF BS-часть ≥ 0.47 (групповой) и ≥ 0.48 (временной); инференс 89 чипов ≤ 20 с на GPU. Без весов — откат на пороги dNBR.
- Цель по качеству (достигалось): IoU_burn 0.764 / mIoU_sev 0.763 (групповой), 0.790 / 0.783 (временной); BS-часть ≈ 0.497 / 0.511.

### F7. `inference.py` — единственная точка входа
- `python inference.py --data-dir <test> --output <csv> [--sample-submission CSV] [--config YAML] [--device auto|cpu|cuda] [--workers N] [--profile]`.
- Коды выхода: 0 — записан и валиден; 1 — записан, но невалиден; 2 — нет данных/конфига (понятное сообщение).
- Шаблон строк: `--sample-submission` → `<data-dir>/sample_submission.csv`.
- CUDA недоступна → CPU с одной строкой предупреждения. Сеть не используется.
- **Приёмка:** на полном тесте (269 чипов) время от старта процесса до валидного файла < 30 с на RTX 4070 (второй запуск; ориентир ≈ 20–23 с); два запуска подряд на одном устройстве — побайтно одинаковы; CPU против GPU — побайтно для одной сети, ≤ 16 пикселей на весь тест для ансамбля (constitution §4); битый/отсутствующий чип → пустая маска, код 0.

### F8. `train.py`
- `python train.py --module af|bs|all [--bs-stages …] [--weights-dir DIR] [--fast]`; пишет веса и строку в `reports/experiments_train.md` (общий `experiments.md` собирается скриптом из модульных журналов и перезаписывается).
- `--fast` — урезанное обучение (меньше эпох), для проверки ТЗ.
- **Приёмка:** AF обучается детерминированно (повтор → побайтно те же веса); BS — разброс ≤ 0.005 BS-части между двумя запусками одной сети (one-hot CE; побайтного повтора нет — см. constitution §4); если GPU-времени на повтор нет — «не проверено» в отчёте.

### F9. REST API сервиса (`service/app.py`)
- `GET /health` → `{"status":"ok", …}`; `GET /docs` — OpenAPI, работает офлайн (Swagger UI локально).
- `GET /api/v1/aoi` — граница территории (GeoJSON FC); `GET /api/v1/chips` — охваты сцен (`properties.kind` = af/bs); `GET /api/v1/dates` — `{gt,pred}.{hotspots,burn_scars}.{date_min,date_max,n}`.
- `GET /api/v1/hotspots` — термоточки (Point; атрибуты `hotspot_id, i4_bt, i5_bt, acq_datetime, satellite, daynight, landcover, confidence, chip_id, source`), `format=geojson|shp`.
- `GET /api/v1/burn-scars` — контуры гарей ((Multi)Polygon; атрибуты `contour_id, severity_class (1–3; 0 — контур события), severity_label, area_ha, date_pre, date_post, chip_id, fire_event_id, source`), `format=geojson|shp` (shp — zip из shp/shx/dbf/prj/cpg).
- `GET /api/v1/summary` — `area_total_ha, by_severity{1..3}{label, area_ha, share_pct}, n_contours, n_fire_events, n_hotspots_day/night, aoi_area_km2, period, crs_note, generated_at`; `format=json|csv`.
- `POST /api/v1/query` — тело `{bbox:[4] | geometry: Polygon, date_from, date_to, source}` → `{hotspots, burn_scars, summary, query_id, meta{n_hotspots, n_burn_scars, elapsed_ms}}`; выгрузка результата — `GET /api/v1/query/{id}/{burn_scars|hotspots|summary}?format=…`.
- Параметры GET: `bbox=minlon,minlat,maxlon,maxlat`, `date_from`, `date_to`, `source=gt|model`. Ошибки валидации — 422 с понятным текстом.
- Контур события (объединение гарей одного события, класс 0) считается на сервере при сборке данных (shapely `unary_union`), а не в браузере.
- Данные сервиса: предрассчитанные слои по 644 train-сценам (у теста нет геопривязки): слой «Эталон» (из масок, лежит в репо сжатым снимком) и слой «Модель» — **только OOF- или holdout-предсказания** наших модулей (plan.md §8), собирается скриптом.
- **Приёмка:** площади в UTM (EPSG 32637/32638) расходятся с `burn_area_ha` из meta ≤ 0.1 % на всех 224 BS-чипах; ответ на весь архив ≤ 1 с; shp открывается geopandas; тесты API на httpx TestClient.

### F11. Docker (CPU)
- `docker build -t firemon .`; `docker run --rm -v <test>:/data:ro -v <out>:/out firemon --data-dir /data --output /out/submission.csv`.
- **Приёмка:** файл побайтно равен venv-прогону; работает с `--network none` и `--cpus 2` (потоки из cgroup). Если Docker недоступен в среде — пропустить с записью, Dockerfile всё равно в репо.

### F12. Тесты
- `python -m pytest -q` зелёный; без данных — тесты, требующие данных, пропускаются с пояснением.
- **Приёмка:** ≥ 60 тестов; покрыты F1–F4, F7 (коды выхода, битый чип), F9.

### F13. Отчёт (`reports/report.md` → PDF)
Разделы строго под критерии (20 баллов): EDA «наблюдение → решение» (≥ 10 пар); разбор baseline (правила-заглушки и почему плохи); эксперименты и абляции с фиксированной валидацией (таблица из журнала, включая отрицательные результаты); инженерные решения (скорость, детерминизм, откаты, переносимость); выводы и ограничения. Лицензии предобученных весов и ПО.
- **Приёмка:** все числа совпадают с `reports/final_numbers.md`; каждый критерий из criteria.pdf имеет раздел. «Прирост» всегда подписан: с чем сравнивали (argmax против argmax, с декодированием или без) — иначе в разных документах окажутся разные числа одного прироста. PDF — через Playwright Chromium.

### F14. README

### F15. Презентация
PPTX, 8–12 слайдов, под 4 минуты: проблема → данные → решение AF → решение BS (ключевой инсайт) → результаты (лестница метрики) → сервис (скриншоты) → скорость и воспроизводимость → выводы. Речь с таймингом в заметках.
- **Подача (обязательно):** заголовок слайда — вывод, а не тема («Public 0.83 — в 2.7 раза выше правил», а не «Результаты»); на слайде одна главная цифра крупно (≥ 60 pt) или одна диаграмма; схема пайплайна — во всю ширину, шрифт ≥ 14 pt; скриншоты — крупно, 1–2 на слайд, с подписями-стрелками; контраст подписей ≥ 4.5:1 (никакого серого на тёмном); заголовок не перекрывает текст (проверить рендером).
- **Приёмка:** открывается в PowerPoint/LibreOffice; все цифры из `final_numbers.md`; есть скриншоты сервиса; превью всех слайдов отрендерено в PNG (LibreOffice `--convert-to pdf` → страницы) и просмотрено — без наложений и пустых половин слайда.

### F16. Скриншоты
≥ 6 скриншотов сервиса (Playwright headless): общий вид, демо-запрос, термоточки крупно, гари по степеням, справка, выгрузка/Swagger. Снимать **после** сборки всех слоёв (включая «Модель») и на подложке «Спутник» (если тайлы доступны), с подписью-аннотацией на каждом кадре (полоса снизу: что показано и какие числа).

### F17. Holdout-оценка (для сравнения версий)
- `python scripts/holdout_eval.py` берёт веса временного сплита (AF и BS, обучены **без чипов 2024 года**), делает инференс по чипам 2024 (`data/test_fake/`) через тот же пайплайн, пишет `out/holdout_submission.csv` + `out/holdout_sample.csv` (шаблон) и печатает Score. Подробно — plan.md §3.3.
- **Приёмка:** файл валиден, Score совпадает с временным сплитом в журнале ±0.005.
