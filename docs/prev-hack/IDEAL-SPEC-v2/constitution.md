# constitution.md — правила проекта

Этот файл — закон для каждого исполнителя. Читается целиком перед любой задачей. Если задача противоречит этому файлу — прав этот файл, а противоречие записывается в отчёт задачи.

## 1. Цель и приоритеты

Сдать за 24 часа рабочее решение кейса «Мониторинг природных пожаров» (см. spec.md). Оценка — 100 баллов, из них только 40 за метрику, 60 — за отчёт, код, сервис, презентацию и скорость. Отсюда порядок приоритетов, когда времени не хватает:

1. валидный `submission.csv` (без него 0 из 40);
2. `README` + `inference.py` + скорость < 30 с (≈ 20 баллов);
3. сервис с REST и картой (12);
4. отчёт (20; пишется из `reports/*.md`, которые ведутся по ходу);
5. презентация (8);
6. дополнительные эксперименты по метрике — в последнюю очередь.

## 3. Окружение и параллельная работа (жёстко)

- **Один venv на один рабочий каталог.** Никаких junction/symlink на `data`, `weights`, `.venv` между каталогами. `pip install -e .` — только в venv, принадлежащем этому каталогу (общий venv на несколько копий репо перенаправляет импорты в чужую копию). Точки входа (`inference.py`, `train.py`, `scripts/*`) работают и без установки: одна строка bootstrap добавляет `src/` в путь.
- Параллельные исполнители работают **в разных файлах** (владение — tasks.md); в одном каталоге — только если никто из них не делает git-операций (коммитит оркестратор). Если нужен общий файл (README, `reports/experiments.md`) — пишет только его владелец; остальные присылают текст в своих отчётах.
- Данные `data/` — одна копия, только чтение, путь передаётся аргументом `--data-dir` или переменной `FIREMON_DATA`. Кэши — в `data_cache/` (в .gitignore), у каждого модуля свой подкаталог.
- Веса экспериментов — `weights_exp/<имя>/`, в финальный `weights/` кладёт только владелец модуля после принятия.
- Команды — PowerShell-совместимые; пути — `pathlib`; никаких абсолютных путей машины разработчика в коде.
- Все пути к данным — через `firemon.io.win_path()` (каталоги `aux`, см. data.md §2).
- `num_workers=0` в DataLoader на Windows (или `if __name__ == "__main__"` + spawn); число потоков — `min(os.sched_getaffinity / cgroup-квота, 16)`, **не** `os.cpu_count()` (в контейнере с квотой он врёт).
- Docker: собирать только CPU-образ. GPU-образ не собирать на машине разработки (раздувает диск, вешает демон).

## 4. Соглашения по коду

- Структура репозитория — plan.md §2. Не менять без записи в отчёте.
- Детерминизм: `seed_everything(42)` (random, numpy, torch, `cudnn.deterministic=True`, `cudnn.benchmark=False`, TF32 выключен); LightGBM `deterministic=True, force_row_wise=True`, фиксированный `num_threads`. **Взвешенный `F.cross_entropy` на CUDA недетерминирован в backward** — использовать CE через one-hot (`-(onehot * log_softmax * w).sum()`), см. plan.md §5.3. Backward nearest-upsample в декодере UNet на CUDA тоже недетерминирован, поэтому **обучение BS побайтно не повторяется** даже с one-hot CE; требование — повтор в пределах ±0.005 BS-части, проверяется контрольным повтором одной сети, если есть GPU-время (иначе записать «не проверено»). Инференс обязан быть побайтно детерминированным.
- Веса: файл ≤ 50 МБ. resnet34-UNet с 50 входами в fp32 весит 98 МБ → хранить `state_dict` в fp16 (≈ 49 МБ), при загрузке приводить к fp32 (на результат инференса не влияет — проверить побайтным сравнением сабмита).
- `.gitignore` — **только якорные шаблоны** (`/data/`, `/data_cache/`, `/weights_exp/`, `/out/`, `/.venv/`): шаблон `data/` без якоря отрезает `service/data/` (эталонный слой сервиса в git) — сервис в чистом клоне падает с 500.
- Отчёт в PDF — markdown → HTML → PDF через Playwright Chromium (pandoc/LaTeX не ставить).
- Инференс: UNet в fp32, без TTA, без TF32, cuDNN deterministic и без benchmark. Два запуска на одном устройстве — побайтно один файл (обязательно). GPU против CPU: для одной сети — побайтно; для среднего нескольких сетей свёртки на CPU и cuDNN округляются по-разному, допускается расхождение ≤ 16 пикселей на весь тест (≈ 23 млн пикселей, влияние на метрику < 1e-6) — тест с этим порогом, честная формулировка в README.
- Никакой зависимости от `chip_id`, порядка чипов, координат, дат (правила, §5). Положение пикселя внутри чипа использовать можно.
- Любой сбой одного чипа → пустая маска + предупреждение в лог; пайплайн не падает. Нет весов модели → откат на правило (`fallback`) + ошибка в лог; валидный файл важнее падения.
- Тесты: pytest, `python -m pytest -q` зелёный перед завершением задачи. Тесты, которым нужны данные, делают `skip` с пояснением, если данных нет.
- Коммиты — маленькие, осмысленные; перед завершением задачи `git status` чистый. Документацию коммитить пакетами (3–4 правки — один коммит), а не по строчке.

## 5. Правила соревнования (нарушение = дисквалификация)

- Только открытое и бесплатное ПО; предобученные веса — только публичные до старта, с лицензией в отчёте (resnet34 ImageNet из torchvision — можно).
- Нельзя использовать данные о территориях/датах тестовой выборки, готовые продукты FIRMS / VNP14 / MCD64A1 / FireCCI и т.п.
- Нельзя восстанавливать геопривязку или даты тестовых чипов и размечать тест вручную. Модели работают только с содержимым чипа и полями тестового `meta.csv`.
- Никаких внешних данных для обучения.
- Организаторы могут перезапустить инференс по README — README должен быть исчерпывающим.

## 6. Эксперименты

- Валидация фиксирована с первого часа (plan.md §3.2): групповые 5 фолдов + временной сплит (val = 2024). Файлы фолдов — в `configs/`, не менять.
- **Правило принятия: прирост ≥ 0.005 соответствующей части Score на ОБОИХ сплитах.** Меньше или разнонаправлено — шум, отклонить, записать.
- Каждый эксперимент — строка в `reports/experiments.md`: время, модуль, гипотеза, конфиг, seed, метрики на обоих сплитах, время, решение. Нет строки — эксперимента не было.
- Тупик объявляется по данным, а не по надежде: если оракул-проверка (идеальная версия идеи) даёт < +0.01, идею не реализовывать; если две разные реализации одной идеи не дали прироста — идею закрыть.
- Шум обучения UNet между фолдами/запусками ≈ ±0.02 IoU. Поэтому промежуточный фильтр «+0.01 на двух фолдах» для гипотез UNet не годится (даёт ложные срабатывания) — решение только по стеку на всех 5 фолдах + временном сплите.
- Одна GPU: пока идёт обучение, исполнителям без GPU-задач **запрещено** запускать тесты и скрипты, использующие CUDA (`CUDA_VISIBLE_DEVICES=""` для pytest документационных задач). Иначе обучение замедляется в 3 раза (измерено: эпоха 7 → 25 с).
- GPU-обучения вести очередью (скрипт-очередь с логом `exit`-кодов), а стек/приёмку — автоматическим запуском по готовности OOF: оркестратор не держит исполнителя в ожидании GPU.
- Список закрытых тупиков — plan.md §6. Не повторять их.

## 7. Отчёт исполнителя (в конце каждой задачи)

В ответе и в `reports/tasklog/<NN>_<имя>.md`: что сделано; файлы; как запустить; тесты (сколько прошло); метрики; время; **открытые вопросы и найденные несостыковки** (самый ценный раздел); что поправить в этом файле.

## 8. Запреты

- Не коммитить данные, кэши, веса > 50 МБ на файл, секреты.
- Не держать служебные заметки агентов (CLAUDE.md, журналы оркестрации) в публичной части репозитория — они живут вне `repo/` или в `.gitignore`.
- Не ставить Docker GPU-образ, не заливать данные в облако, не трогать чужие каталоги.
- Не устраивать «ещё одну попытку» по закрытому тупику (plan.md §6) без новой оракул-проверки.
