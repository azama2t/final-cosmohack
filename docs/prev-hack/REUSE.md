# REUSE — что вынести в шаблон для будущих хакатонов

Цель шаблона — чтобы первый час следующего хакатона уходил на постановку и разведку данных, а не на RLE, метрику, сплиты и скелет сервиса. По ретро и аудитам 01–03 это экономит 2–3 часа (оценка) и снимает три класса аварий (окружение, формат сабмита, детерминизм).

Размеры — по аудиту 03 (текущие строки в репозитории `fire-monitoring`).

## 1. Ядро репозитория (переносить как есть, параметры — в конфиг)

## 4. Приёмы ML (переносить как методику)

| Приём | Где сработал | Когда применять |
|---|---|---|
| **Разведка эталона** в первый час: «каким алгоритмом построена разметка, что из неё выводимо из входа» | AF ≈ пороги VNP14; BS-степень = пороги dNBR по покрову (97 %), буфер события ≈ 4 км | всегда: определяет архитектуру и потолок |
| Кандидаты по порогам → градиентный бустинг на кандидатах + hard negatives в кольце | AF: F1 0.968 против 0.917 у CNN, 4 с на 180 чипов | точечные редкие аномалии |
| UNet выбирает регион → бустинг 2-го уровня в «воротах» (p > gate) восстанавливает границы и классы | BS: 0.389 (LGBM) → 0.496 | когда классы задаются правилом, а трудность — «какой объект целевой» |
| Оракул-проверка перед реализацией | закрыла бы 4 тупика за 15–60 мин | каждая гипотеза |
| Правило принятия «≥ δ на обоих сплитах» + измерение шума повтором обучения | отсеяло ≈ 40 ложных улучшений | каждая серия гипотез |
| Жадный подбор декодирования и постобработки по OOF, запись в json рядом с весами | +0.006…0.010 BS | сегментация с порогами |
| Многомасштабное обучение (0.75×, 0.5×) для контекста | +0.005 / +0.011 | «какой объект в кадре целевой» |
| Детерминизм: fp32, без TTA/TF32, one-hot CE вместо weighted CE на CUDA | побайтно один файл на GPU/CPU/Docker | всегда, если организаторы перезапускают |
| Фоновой прогрев `import torch` пока читаются данные | холодный старт 42 → 28 с | порог скорости |

## 5. Процессные активы

- `ORCHESTRATOR-PROMPT-v2.md` — регламент оркестратора (время, параллелизм, сдача, формулировки).
- `IDEAL-SPEC/constitution.md` как шаблон правил проекта (стек, окружение, детерминизм, правило принятия, формат отчёта исполнителя).
- Шаблон задания исполнителю (цель, контекст с цифрами и следствием, вход/выход, критерии, правило принятия, бюджет, отчёт с «открытыми вопросами»).
- Шаблон ночного автономного режима: очередь гипотез с оракулом, правило принятия, журнал, стоп-условие, очередь запасных задач.
- `METRICS.md`-шаблон: таймлайн фаз, по исполнителю время/токены/статус.

## 6. Что в шаблон НЕ брать

- Скрипты экспериментов (`scripts/bs_night_*`, `bs_*check`, 40 файлов), модули отклонённых гипотез (`components.py`, AF-`postprocess.py`), мёртвые функции (`predict_af`, `predict_bs`) — аудит 03.
- 9 файлов requirements (достаточно трёх), дублирующие конфиги, `Dockerfile.gpu`.
- `sys.path.insert` в каждом файле (33 места) — одна строка bootstrap в точках входа.
- Веса в git без LFS (205 МБ) — веса отдельно, скрипт скачивания/сборки.
- CLAUDE.md и журналы агентов внутри публичного репо.
