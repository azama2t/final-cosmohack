# OCEAN EVIDENCE — UX / VISUAL REFINEMENT PASS

Ты работаешь с уже существующим фронтом Ocean Evidence, который в целом функционально сильный и покрывает практически все критерии кейса.

ВАЖНО:
- не переписывай продукт с нуля;
- не выкидывай существующие фичи;
- не ломай рабочие сценарии;
- не заменяй реальную функциональность красивыми заглушками.

Наша задача — сделать интерфейс заметно понятнее, сильнее визуально и логичнее по пользовательскому сценарию.

Главная проблема текущей версии:
**почти всё нужное уже реализовано, но часть функций спрятана слишком глубоко, часть состояний выглядит как ошибка продукта, а некоторые визуальные решения мешают понять, что вообще происходит.**

Открой и внимательно изучи все скриншоты в папке `screenshots/`.

## 1. TIMELINE — НУЖЕН ЯВНЫЙ И ПОСТОЯННО ДОСТУПНЫЙ ВРЕМЕННОЙ СЛОЙ

### Проблема

В текущем интерфейсе нет очевидного timeline как одного из ключевых инструментов анализа.

Для задачи, где:
- есть спутниковые сцены;
- есть полевые измерения;
- есть даты;
- есть повторные наблюдения;
- есть моделирование/дрейф;
- есть проверка совпадений между сценами,

отсутствие явной временной оси воспринимается как серьёзное UX-опущение.

### Требование

Добавь timeline как **первоклассный элемент интерфейса**, а не спрятанную вторичную функцию.

Timeline должен:
- быть заметен пользователю сразу;
- показывать доступные спутниковые сцены;
- показывать полевые наблюдения;
- выделять текущую выбранную дату/сцену;
- позволять перемещаться по времени;
- синхронизироваться с картой и выбранным объектом;
- поддерживать zoom по времени;
- показывать интервалы моделирования/дрейфа отдельно от наблюдений;
- визуально различать реальные измерения, спутниковые сцены и прогноз/эксперимент.

НЕ делай обычный slider.

Нужна временная рабочая область, похожая по логике на профессиональный editor timeline, но адаптированная под Earth Observation.

## 2. ИНФОРМАЦИОННАЯ ПЛАШКА / OVERLAY ПРОПАДАЕТ В КАРТЕ

Смотри `02_list_overlay_bug.png`.

### Проблема

Дополнительная информационная плашка открывается так, что:
- частично уходит за карту / соседнюю область;
- текст обрезается;
- пользователь теряет контекст;
- ощущается как layout bug, а не намеренная панель.

### Требование

Все context overlays / tooltip / info panels должны:
- оставаться полностью внутри viewport;
- автоматически менять сторону открытия;
- не обрезаться родительским контейнером;
- иметь правильный z-index;
- не перекрывать критичную информацию без необходимости;
- закрываться предсказуемо;
- работать при разных размерах окна.

Используй collision-aware positioning: например Floating UI / Radix Popover primitives или аналогичный устойчивый механизм.

Проверь на:
- 1366×768;
- 1440×900;
- 1920×1080.

## 3. DRIFT SIMULATION СЕЙЧАС ВЫГЛЯДИТ ФИЗИЧЕСКИ НЕПРАВДОПОДОБНО

Смотри `03_drift_simulation_problem.png`.

### Проблема

После запуска прогноза дрейфа появляется огромное количество точек/частиц.

Визуально это создаёт ощущение, будто система внезапно «создала» больше мусора, чем существовало в исходной зоне.

Это плохо как с точки зрения UX, так и с точки зрения научной честности.

### Требование

Раздели:

**исходные наблюдаемые/обнаруженные объекты**
и
**модельные частицы / uncertainty ensemble**.

Если прогноз строится Monte Carlo / particle ensemble:
- никогда не создавай впечатление, что каждая частица = новый предмет мусора;
- явно подпиши: `частицы модели`, `ensemble`, `сценарии траекторий` или аналогично;
- количество model particles НЕ должно визуально читаться как predicted item count;
- используй прозрачность/плотность/flow field вместо сотен одинаковых "объектов";
- желательно показывать центральную/наиболее вероятную траекторию;
- uncertainty corridor / envelope;
- несколько representative particles;
- исходную зону.

Лучший визуальный вариант:

SOURCE ZONE → основной вектор/траектория → uncertainty plume/corridor → несколько representative particles.

Если физическая модель не подтверждена, обязательно оставить явный статус:

**Экспериментальный прогноз. Не является наблюдением.**

Не обещай количество предметов из числа model particles.

## 4. "SERVICE UNAVAILABLE" НЕ ДОЛЖЕН ЛОМАТЬ ПРОДУКТ

Смотри `04_quality_service_unavailable.png`.

### Проблема

Раздел "Проверка качества" иногда превращается почти целиком в `Сервис недоступен`.

Это выглядит как сломанная фича и очень плохо для демо.

### Требование

Сделай graceful degradation.

Если backend quality service недоступен:
1. Не показывай огромную пустую область.
2. Сохраняй последний доступный результат, если он есть.
3. Покажи компактный статус: `Сервис проверки качества временно недоступен`.
4. Покажи время последней успешной проверки.
5. Если возможно, отображай локально вычисляемые quality indicators.
6. Добавь `Повторить`.
7. Не скрывай основной рабочий продукт из-за одного unavailable endpoint.

Для демо интерфейс всё равно должен выглядеть полностью собранным и осмысленным.

НЕ подменяй реальные данные фейковыми.

## 5. PHOTO COUNTER — СИЛЬНАЯ ФИЧА, НО СЕЙЧАС ОНА СЛИШКОМ ОТДЕЛЕНА ОТ ОСНОВНОГО ПРОДУКТА

Смотри `05_photo_counter_module.png`.

### Что здесь хорошего

Есть реальная отдельная функция:
- пользователь загружает детальное фото;
- detector находит отдельные предметы;
- показываются bbox;
- confidence;
- object count;
- threshold;
- можно задать площадь/GSD;
- можно получить шт./км² при известной площади;
- присутствует честное описание ограничений.

Это очень важная часть решения, потому что спутник Sentinel-2 не умеет напрямую считать мелкие отдельные предметы.

### Проблема

Функция ощущается как отдельное приложение, спрятанное за `Фото`.

### Требование

Интегрируй её в основной пользовательский сценарий.

Пользователь должен быстро понимать:

### Спутник
ищет зоны / скопления / evidence.

### Детальное фото / drone / near-water camera / VHR
считает отдельные видимые объекты.

В основном интерфейсе должна существовать заметная точка входа:
- `Посчитать предметы по фото`
или
- `Детальное изображение`.

Также при выборе observation / zone, если существует связанное детальное изображение, должна быть кнопка:

**Открыть детальный снимок**

и пользователь сразу попадает в этот модуль с выбранным контекстом.

## 6. CRITERIA COVERAGE — НЕ ПРЯТАТЬ СИЛЬНЫЕ ФИЧИ

Текущая система создавалась с целью закрыть критерии кейса максимально полно.

Функций уже много.

Проблема не в отсутствии capability.

Проблема: **пользователь и жюри не должны искать важные функции по пяти уровням меню.**

Проведи полный UX audit всех существующих возможностей.

Для каждой функции ответь:
- насколько она важна для кейса?
- увидит ли её человек за первые 30–60 секунд?
- нужно ли вынести её выше?
- должна ли она быть постоянно видима?
- нужна ли она только экспертам и может быть спрятана глубже?

## 7. СФОРМИРУЙ 3 УРОВНЯ ИНФОРМАЦИИ

### LEVEL 1 — ВИДНО СРАЗУ

То, что жюри/пользователь должен понять за 5–10 секунд:
- где мы;
- какая сцена/дата;
- сколько evidence / находок;
- есть ли подтверждение;
- основная карта;
- timeline;
- текущий режим;
- ключевая зона/наблюдение;
- путь к детальному фото;
- качество/достоверность кратко.

### LEVEL 2 — ОДИН КЛИК

- scene details;
- zone inspector;
- field measurement;
- quality details;
- drift scenario;
- сравнение;
- provenance;
- export.

### LEVEL 3 — ЭКСПЕРТНЫЕ ДЕТАЛИ

- model parameters;
- raw metadata;
- thresholds;
- exclusions;
- full provenance;
- scientific notes;
- API/debug details.

Не заставляй LEVEL 1 тонуть в LEVEL 3.

## 9. LOCAL ANALYSIS — ПЕРЕСТРОИТЬ ВОКРУГ СЦЕНЫ

При переходе в локальный анализ пользователь должен видеть:
1. карту / satellite scene;
2. зоны detector;
3. field observations;
4. явный timeline;
5. выбранную zone/evidence;
6. короткий verdict;
7. путь к подробностям;
8. путь к детальному фото, если оно существует.

Правый inspector полезен, но сейчас информации много.

Перестрой его по progressive disclosure.

Сначала:
- Что это?
- Подтверждено или нет?
- Почему?
- Можно ли оценить количество?
- Есть ли детальное изображение?
- Есть ли field evidence?

Остальное ниже.

## 10. КОЛИЧЕСТВО ПРЕДМЕТОВ — ЧЕСТНАЯ АРХИТЕКТУРА

Не создавай впечатление, что Sentinel-2 напрямую считает отдельные бутылки.

Разделение должно быть очевидно даже в UI:

### Satellite / EO
`обнаружение скопления / зоны`

### Detailed imagery
`подсчёт видимых отдельных предметов`

### Field
`независимое измерение / шт./км²`

Если количество по спутнику недоступно:

`Количество предметов по этой спутниковой сцене не определено`.

Это лучше, чем fake precision.

## 11. ПРОГНОЗ ДРЕЙФА — ОТДЕЛИТЬ ОТ OBSERVED DATA

Используй отдельную semantic language:

OBSERVED / FIELD — синий / нейтральный evidence

SATELLITE DETECTION — янтарный / orange

SIMULATION / DRIFT — фиолетовый или другой отдельный experiment color

Но simulation не должна выглядеть как новый набор реальных мусорных объектов.

## 12. ИНФОРМАЦИОННАЯ АРХИТЕКТУРА ДЛЯ ДЕМО

Подготовь понятный demo flow:

1. Земля / глобальный обзор.
2. Выбираем сцену с находками.
3. Переходим в локальный анализ.
4. Timeline показывает scene + field events.
5. Выбираем detected zone.
6. Inspector объясняет verdict.
7. Если есть полевая запись — показываем relation.
8. Если есть detailed image — открываем object counter.
9. При необходимости показываем drift как эксперимент.
10. Quality / provenance.
11. Export.

Все эти шаги должны находиться быстро.

## 13. VISUAL CLEANUP

Текущий frontend уже выглядит сильнее среднего хакатонного решения.

Не уничтожай его композицию.

Но исправь:
- слишком плотные списки;
- text truncation;
- overflow overlays;
- слабые selected states;
- слишком большое количество одинаково важных строк;
- мелкие critical labels;
- плохо заметные сильные функции.

Сделай primary information визуально сильнее.

## 14. НЕ ЛОМАЙ 100-БАЛЛЬНОЕ ПОКРЫТИЕ

Перед изменениями составь краткую матрицу:

CRITERION / FEATURE / CURRENT LOCATION / NEW LOCATION

Не удаляй feature только потому, что он визуально мешает.

Если функция важная, но перегружает главный экран — перенеси её в правильное место.

## 15. QA

После исправлений обязательно проверить:

### Timeline
- сцены;
- field events;
- selection;
- zoom;
- map sync.

### Overlays
- не выходят за viewport;
- не clip'аются.

### Drift
- model particle count визуально не выглядит как item count;
- simulation ясно обозначена.

### Offline/service unavailable
- продукт остаётся целым;
- нет огромных пустых состояний.

### Photo counter
- доступен из понятного места;
- работает upload;
- сохраняются bbox/count/confidence;
- площадь → items/km² только когда площадь реально задана.

### Criteria
- все существующие capability остаются доступными.
